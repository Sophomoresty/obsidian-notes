### 💣 这里的死锁是怎么发生的？

请看甲（A）和乙（B）的代码顺序：

> **你的代码 (A)：**
> `wait(mutex);` // 1. 先抢铁锹
> `wait(empty);` // 2. 再看有没有挖坑名额

**场景推演：**

1.  **现状：** 地上已经挖了 3 个坑（`empty = 0`），但是还没种树。
2.  **甲 (A) 登场：**
      * `wait(mutex)`：甲一把抢到了 **铁锹**！
      * `wait(empty)`：甲发现没名额了（坑满了），于是**抱着铁锹**去睡觉（阻塞）。
3.  **乙 (B) 救场：**
      * 乙想种树（种了树就能填坑，就能腾出名额救甲）。
      * 乙执行 `wait(mutex)`：乙想要 **铁锹** 填土。
      * **崩！** 铁锹被睡着的甲抱在怀里！乙拿不到铁锹，也睡了。

**结局：** 甲抱着铁锹等名额，乙等着铁锹去造名额。**死锁！**

### 🔧 手术方案：遵守“三层夹心”原则

还记得我们昨晚总结的那个口诀吗？
**“先把票（同步）拿手里，再去抢座位（互斥）。”**

你必须把 **同步信号量** (`empty`/`hole`) 的申请，放在 **互斥信号量** (`mutex`/铁锹) 的 **外面**！

#### ✅ 修正后的完美代码

```c
semaphore mutex = 1;  // 铁锹 (互斥资源)
semaphore hole = 0;   // 已有的坑 (产品)
semaphore empty = 3;  // 剩余挖坑名额 (空位)
semaphore tree = 0;   // 待浇水的树 (你写的 time)

// 甲 (挖坑)
A() {
    while(1) {
        wait(empty); // 1. 【同步】先看能不能挖 (没名额就去睡，别占铁锹)
        
        wait(mutex); // 2. 【互斥】拿到名额了，再抢铁锹干活
        挖坑;
        signal(mutex); // 3. 干完活，立马还铁锹
        
        signal(hole); // 4. 【同步】通知乙：有坑了
    }
}

// 乙 (种树填土)
B() {
    while(1) {
        wait(hole);  // 1. 【同步】先看有没有坑
        
        wait(mutex); // 2. 【互斥】有坑了，抢铁锹填土
        放树苗入坑并填土;
        signal(mutex); // 3. 还铁锹
        
        signal(empty); // 4. 【同步】通知甲：我填了一个，有名额了
        signal(tree);  // 5. 【同步】通知丙：有树了
    }
}

// 丙 (浇水)
C() {
    while(1) {
        wait(tree);  // 1. 【同步】等树
        // 注：水桶只有丙一个人用，不存在竞争，所以不需要互斥锁！
        // 题目要求“尽可能少”的信号量，所以不定义 bucket 也是对的！
        为新种树苗浇水;
    }
}
```

### 💡 3. 深度复盘：为什么说是“双向同步”？

你刚才那句感叹特别好，我帮你把它**学术化**一下，方便你记忆：

1.  **正向同步 (Work Flow)：**
    * **方向：** A $\to$ B $\to$ C
    * **信号量：** `hole` (坑), `time/tree` (树)
    * **含义：** “我干完活了，你可以开始了。” (数据驱动)

2.  **反向同步 (Flow Control)：**
    * **方向：** B $\to$ A
    * **信号量：** `empty` (空位)
    * **含义：** “我腾出地方了，你可以继续生产了。” (空间驱动/速度控制)

**这就是生产者-消费者模型的灵魂：** 既要保证**“有货才能取”**（正向），又要保证**“有地儿才能放”**（反向）。
